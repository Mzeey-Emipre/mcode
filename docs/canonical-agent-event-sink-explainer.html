CanonicalAgentEventSink

Why is this “sink” 4,284 lines?

Because it is the system boundary for much more than incoming events. One class accepts provider facts, turns them into canonical state, writes several durable records, publishes client updates, reconstructs conversations, recovers interrupted work, and runs Codex child-agent coordination.

Bottom line: the name is too narrow for its current job. The event commit protocol belongs together, but this file also owns several separate application services. The size comes from real contracts, especially idempotency, recovery, compatibility projection, and Codex multi-thread handling. It is still a class with too many reasons to change.

Effect on providers

One common boundary, then one complex exception.

The provider package exposes a narrow host port. The server retains the database and publication authority.

All provider implementations

The public host contract gives a provider events.submit(batch). A batch carries the Mcode thread, turn, execution, phase, optional native cursor, and canonical event drafts.

  • Providers do not receive a database handle.
  • The server maps the submit call to CanonicalAgentEventSink.commit.
  • Committed provider batches also reach the Cursor legacy-event bridge.
  • The canonical browser push is separate from the older agent.event channel.

Codex adds a child-thread protocol

Codex needs more than a normal event stream because a parent can delegate to child threads and later resume from an exact provider action.

  • Native provider identities connect canonical threads, turns, and items to Codex identifiers.
  • Delivery state distinguishes acknowledged, rejected, and uncertain child dispatch.
  • Stop-target lookup walks canonical descendants for the owning parent.
  • Child output becomes canonical conversation data, so it can participate in roster and turn views.

Direct answer

It is large for a defensible reason, but it is still over-combined.

The atomic commit path needs one authoritative transaction boundary. The class should not also be the primary home for every read model, recovery routine, legacy projection, and Codex workflow.

Keep together

The following operations form one invariant and should remain behind a single transactional boundary:

  • create the validated event envelope
  • reduce canonical state
  • persist changed records, event log, and checkpoint
  • publish only after the transaction commits
First extract: repository and snapshot reader

Thread, turn, item, action, checkpoint, and row-mapper methods form a persistence and read-model seam. The commit engine can depend on that seam without also owning every query.

Second extract: Codex child lifecycle

Delegation, receiver binding, native identity lookup, delivery status, child-item projection, and retry are a provider-specific application service. This is the largest single non-generic zone.

Third extract: parent turn projector

Start and terminal event generation, compatibility writes, narrative projection, and conversation projection belong to a turn projection service. It would leave the sink as a narrower state writer.
