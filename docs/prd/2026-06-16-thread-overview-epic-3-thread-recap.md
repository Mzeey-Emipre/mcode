## Problem Statement

I cannot tell at a glance what a thread is about. The thread title is terse and deterministic, and to remember what a thread was doing I have to scroll back and read it. With several threads open, re-orienting on each one is friction. I want a plain-language line that tells me what I am working on in this thread - but not at the cost of token spam from a model that fires on every turn or for threads I never look at.

## Solution

A short AI-generated one-line recap at the top of the Overview - "what you're
working on" for the active thread. It is generated cheaply and lazily: the user
can request it from the row, and the app may generate it automatically when the
user returns to a stale thread. In Mcode, returning includes app focus return,
switching back to a thread, and opening the Overview. The default stale threshold
is about five minutes since the last completed turn. It never fires mid-turn,
dedupes by conversation signature, sends bounded material, and caches the result
for the session.

## User Stories

1. As a developer, I want a one-line recap of what a thread is doing at the top of its Overview, so that I can re-orient without reading the transcript.
2. As a developer, I want to request a fresh recap when the line is stale or wrong, so that I am not stuck waiting for an automatic refresh.
3. As a developer, I want the recap to cost near-zero tokens, so that the feature does not waste my budget.
4. As a developer, I want the app to refresh the recap when I return to a stale thread, so that switching back after time away re-orients me.
5. As a developer, I want thread switches to count as returns, so that Mcode's multi-thread workflow gets the same benefit as terminal focus return.
6. As a developer, I want the stale threshold to be about five minutes, so that the app does not spend tokens for short pauses.
7. As a developer, I want auto recap to wait until the thread has enough conversation to summarize, so that short threads do not trigger empty model calls.
8. As a developer, I want the recap to wait until the thread is idle, so that it does not fire mid-turn or while the assistant is streaming.
9. As a developer, I want the recap to regenerate only when the conversation materially changes, so that tool noise and work-log churn do not trigger it.
10. As a developer, I want a refresh to send only the new messages since the last recap plus the previous recap, so that re-summarizing the whole transcript does not waste tokens.
11. As a developer, I want auto recap capped per thread and signature, so that repeatedly switching threads does not create hidden spend.
12. As a developer, I want the recap cached for the session, so that reopening the Overview does not regenerate it.
13. As a developer who restarts the app, I want the first eligible return per thread to regenerate the recap once, so that the in-memory reset is acceptable and predictable.
14. As a developer, I want the recap clipped to a short single line, so that it fits the Overview row.
15. As a developer, I want the row to show when the cached recap is stale or unavailable, so that I can decide whether to spend a manual refresh.

## Implementation Decisions

- **Stateless generation RPC.** A new `recap.generate` RPC takes the client-selected bounded material (`threadId` for telemetry only, `messages`, `previousRecap`) and returns `{ text }`. The server stores nothing - no table, no migration, no thread-row field. This is the deliberate divergence from the durable diff Summary.
- **Server prompt builder.** A `RecapService` with a pure `buildThreadRecapPrompt(messages, previousRecap)` and `sanitizeThreadRecap(text)` (mirroring `buildDiffSummaryPrompt` and Synara's `textGenerationShared`), calling `UtilityCompletionService.complete` (our haiku utility model, low reasoning effort, not Synara's `gpt-5.4-mini`). The prompt instructs the model to return the previous recap unchanged when nothing material changed. Output clipped to ~220 chars.
- **In-memory client cache.** `threadStore` gains `recapByThread: Record<threadId, { text, signature, coveredMessageId, generatedAt, autoGeneratedAt? }>` or an equivalent shape, never persisted, dropped by `clearThread`. On restart the first eligible return per thread can regenerate once after the stale threshold.
- **A trigger hook owns all gating.** A `useThreadRecap` hook owns manual generation, auto generation on stale-thread re-orientation, signature gating, in-flight gating, failure gating, the auto-call cap, and delta assembly. Re-orientation means app focus return, switching back to a thread, or opening the Overview. Auto generation requires the last completed turn to be at least about five minutes old, enough user/assistant conversation to summarize, a changed signature, no running turn, and no matching cached/in-flight/last-failed request. Manual generation can bypass the stale-time threshold but still dedupes same-signature and in-flight requests. Incremental refresh sends only the delta since `coveredMessageId` - bounded to ~4 messages, ~600 chars each - plus the previous recap. First pass is bounded to ~6 messages.
- **Recap row states.** The row renders cached text, a stale indicator when newer user/assistant material exists, a small manual refresh action, a quiet pending state while generation runs, and a quiet unavailable state after failure. The row does not auto-loop on failure.
- **No hot-path coupling.** The hook is an opt-in side effect of the open panel and must never run from the transcript render or the turn-event path.

## Testing Decisions

- A good test asserts the decision the system makes - whether to schedule a generation, and the prompt/output shape - not the React hook internals.
- **Modules tested:** the pure `buildThreadRecapPrompt` / `sanitizeThreadRecap`, the pure scheduling decision (`shouldScheduleThreadRecapGeneration`) and signature hash, and the `recapByThread` cache cleanup.
- **Prior art:** `diff-summary-prompt.test.ts` tests `buildDiffSummaryPrompt` as a pure function with no mocks - mirror it for the recap prompt and sanitizer. `utility-completion-service.test.ts` mocks the provider registry and asserts `complete()` - reuse that path; the recap RPC handler stays a thin pass-through and is not separately unit-tested (consistent with `diffSummary.*`). Synara's `threadRecap.ts` is the model for the pure scheduling decision. The hook's end-to-end behavior is covered by the Overview E2E (panel-gated, no call when closed).
- Cases to add: the scheduler returns false when the thread is not stale enough, too short, mid-turn, signature-unchanged, in-flight, last-failed for the same signature, or over the auto cap; returns true on app focus return, thread switch return, and Overview open when the thread is stale and materially changed; manual refresh bypasses stale-time gating but not in-flight and same-signature dedupe; the prompt includes the previous recap and only the delta; sanitize clips to the char cap; `clearThread` drops the cache entry.

## Out of Scope

- Persisting the recap server-side or in localStorage (Synara's choice) - intentionally in-memory.
- Eager, per-turn, or rolling quiet-period generation.
- Persisting stale indicators or recap state across restarts.

## Further Notes

This epic carries the user's one hard constraint - no token spam - which is why its cost control is isolated here rather than folded into the surface epic. It hard-depends on Epic 2 for the panel and the Overview row. Synara remains useful prior art for cache shape and bounded deltas. Claude Code is the better product reference for user-triggered recap and auto recap after returning from time away.
