Agent control for the Browser users already see

Mcode already has the visible browser, tabs, CDP access, capture, redaction, and memory saver. The implementation should add a secure provider gateway and a collaborative control layer, while keeping the current Browser surface intact.

Architecture decision

Expose high-level browser_* tools through a loopback MCP server. Route each provider session to one live desktop and one Browser tab. Execute the actions against the adopted webview, with immediate human interruption.

01

Target architecture

One request crosses five owned boundaries. Each boundary validates only what enters it, then passes a typed value to the next layer.

01Provider sessionCodex, Claude, Cursor, or GitHub Copilot calls an MCP tool.
02MCP gatewayAuthenticates the scoped token and validates arguments.
03Sticky brokerKeeps a session assigned to one desktop and tab.
04Control kernelSerializes actions and arbitrates human input.
05Browser webviewUses the visible page, cookies, storage, and DOM.

No second browser: the agent and user share one Electron guest. A separate Playwright browser would create different cookies, focus, history, and page state.

Server ownsIdentity and routing

MCP transport, hashed credentials, provider lifecycle, capability discovery, sticky assignments, pending requests, timeouts, and cancellation.

Desktop ownsBrowser execution

Webview adoption, CDP attachment, action semaphore, control epochs, native input, tab targeting, diagnostics, and cleanup.

Web ownsVisible collaboration

Browser panel state, controller indicator, agent pointer, focused target treatment, stop action, and typed unavailable states.

03

Provider tool contract

Use Mcode's Browser language and expose semantic operations. Raw CDP remains inside Electron.

browser_openReveal the current thread's Browser and create a tab only when needed.UI
browser_inspectReturn the current tab observation, readiness, capabilities, diagnostics, and optional PNG.READ
browser_actExecute a bounded, observation-bound batch of Browser steps.WRITE
browser_tabsSelect, claim, release, close, or finalize assigned Browser tabs.LIFECYCLE
browser_evaluateEvaluate bounded JavaScript in an isolated world for Full Build sessions.PRIVILEGED
Privileged operation: browser_evaluate is available only to Full Build sessions. It runs in an isolated world with bounded input, output, and runtime. Resize and recording remain capability-gated when the current Electron surface cannot support them.
04

Security and failure behavior

Browser automation crosses provider, HTTP, live-stream, IPC, guest-content, and URL boundaries. Failure must be typed and closed.

Boundary or failureRequired controlObserved result
Provider credentialAt least 256 random bits, hash-only storage, 30-minute idle expiry, eight-hour absolute lifetime, session revocation.Invalid or expired requests receive HTTP 401 without scope details.
Desktop ownershipMatch worktree, window, thread, tab, webview type, host webContents, partition, contract version, and operation.No compatible owner returns browser_unavailable.
Human inputAdvance a per-tab control epoch on genuine keyboard, pointer, touch, focus, or navigation input.The action stops with browser_interrupted_by_user and releases held keys.
NavigationAllow HTTP and HTTPS only. Reject embedded credentials, local files, internal pages, extensions, and development tools.Blocked targets return browser_navigation_blocked before loading.
Page contentReuse capture redaction, bound every field, mark truncation, and keep typed text and query strings out of logs.Snapshots remain useful without becoming an unbounded data export.
Host or tab lossCancel pending work and keep assignment sticky. Never move an in-flight sequence to another tab.The agent receives browser_target_lost and must observe again.
Guest capabilitiesDeny popups, downloads, clipboard, geolocation, notifications, and other permissions by default.New permissions require a separate reviewed allowlist.
05

Verification protocol

Unit tests lock down boundaries. Integration tests prove routing. Live desktop checks remain the main behavior gate.

Level 1

Contract and unit

  • Schema bounds and URL rejection
  • Credential expiry and isolation
  • Sticky assignment and queue limits
  • Control-epoch interruption and cleanup
  • Snapshot redaction and truncation
  • Webview ownership validation
Level 2

Process integration

  • MCP discovery, auth, calls, images, and cancellation
  • Server-to-desktop request correlation
  • Provider config injection without secret leakage
  • Tab close, cold discard, thread switch, restart, and reconnect
  • Raw-pipe compatibility during migration
Level 3

Live desktop

  • Real provider turn controls a local test app
  • User sees the same cookies and page state
  • Keyboard and pointer interrupt long actions
  • Background, cold, closed, and crashed tabs
  • Windows, macOS, and Linux modifier behavior
  • Permission, popup, redaction, and log checks
Release gate

Each provider must open, navigate, snapshot, click, type, press, scroll, wait, and recover from interruption in the visible Mcode Browser. Focused tests must pass after the live check.

06

Rollout and decisions

The Browser v2 contract stays focused on protocol retirement and remains separate from unrelated Browser redesign.

Provider contract

The typed Browser v2 gateway serves every supported provider session through one scoped MCP contract.

What Mcode keeps

The renderer-hosted Browser webview, tab store, memory saver, active-preview webContents resolver, capture redaction and spill behavior, diagnostics buffers, right panel, provider session runtimes, and permission UI.

What Mcode replaces

The raw provider-facing CDP boundary becomes typed MCP tools with scoped credentials, sticky ownership, bounded operations, human interruption, and provider capability discovery.

Known upstream traps added to acceptance tests

Resize timeouts, poisoned sessions after snapshot failure, missing-target errors, unreliable keyboard input, invisible background tabs, clipboard permission mismatches, recording start and stop races, and WSL loopback rewriting.

Non-goals

No hidden Chromium, external Chrome profile, second browser engine, raw CDP over MCP, automated local-file navigation, unattended cloud browser, or long-term storage of page content.
