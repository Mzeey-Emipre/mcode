Architecture Review · deepening opportunities

When & how do we persist a turn?

Branch plan/narraitive-db-persistance. This report first answers the four questions you asked about the current pipeline, then proposes deepening opportunities — refactors that concentrate the "what does it mean to end a turn" logic behind one small seam, so empty-turn skipping and known-failure retry become single decisions instead of scattered ones.

How it works today

Q1 · real-time or after a turn?

Hybrid, but mostly batched at turn end. The user message is written synchronously inside sendMessage() in a transaction before the agent runs. Everything the agent produces — the assistant message, tool calls, narration segments, hooks — is buffered in memory in NarrativeStore for the whole turn and flushed in one shot at the end.

Q1 · two separate writes, two events

The assistant message body is inserted on the Message event (agent-service.ts:~1573). The narrative rows are inserted later by persistNarrative(), triggered by persistTurn(). Streaming deltas only accumulate in streamingAssistantTextByThread (memory) — nothing persists mid-stream. turn.persisted broadcasts after the DB commit (:2377).

Q2 · error

The Error handler (:1843) checks the last row: if it is an assistant message it calls persistTurn(isError=true) — buffered tool calls still running flip to cancelled (narrative-store.ts:463). If no assistant message exists (pre-turn failure), it discards everything via clearTurnState. No retry exists.

Q2 · cancel (stop button)

stopSession() (:1407) signals the subprocess, then flushInterruptedAssistantMessage() writes the accumulated stream text only if non-empty and no assistant row exists yet, then persistTurn(isError=true) marks running tools cancelled. Stop-before-first-delta writes no assistant row.

Q3 · do we skip no-op turns?

No. The only guard is messages.length === 0 in persistTurn (:2319) — a safety net for "not even a user message exists." A text-only turn, or even an empty-content assistant message, always writes an assistant row because the Message event inserts unconditionally. There is no single "did this turn produce anything recordable?" predicate.

Q4/dedupe · idempotency asymmetry

Narrative rows use INSERT OR IGNORE (tool calls, thoughts, hooks) — safe to re-run. The assistant message uses a plain INSERT (message-repo.ts:~121) — a replayed Message event duplicates the row. persistTurn has a soft re-entrancy guard (persistingThreads Set) that just drops the second call.

Deepening opportunities

Four candidates. The first is the keystone — the other three become cheap once it lands, because they all live behind the same seam.

Candidate 1 · keystone

A single finalizeTurn(outcome) seam

Strong
agent-service.ts — Error / TurnComplete / stopSession handlers agent-service.ts — persistTurn(), flushInterruptedAssistantMessage()

Problem

"Ending a turn" is decided in three places, each re-deriving its own preconditions. The Error handler re-checks "is the last message an assistant?"; persistTurn re-checks "do any messages exist?"; stopSession separately remembers to flush the streaming text first. The outcome (completed / errored / cancelled) is encoded as a bare isError boolean that collapses errored and cancelled into one — which is exactly why running tools can't tell whether they were cancelled vs. killed by a crash. The knowledge of "what a finished turn means" has no home.

Solution

Introduce one deep method — finalizeTurn(threadId, outcome: "completed" | "errored" | "cancelled") — that owns the entire end-of-turn sequence: precondition check, optional flush of interrupted streaming text, persistNarrative, snapshot, broadcast, clear. The three event handlers shrink to a single call each. Outcome becomes a first-class enum instead of a boolean, so cancelled and errored tool-call statuses stop being conflated.

After — deep, one seam owns the meaning

Benefits

  • Locality: every rule about ending a turn — preconditions, flush ordering, outcome mapping — lives in one method. Today a change to that policy means editing three handlers and hoping they stay consistent.
  • Leverage: the interface is one enum argument behind the whole persist/snapshot/broadcast dance. Candidates 2–4 plug in here as small internal decisions instead of new scattered branches.
  • Tests: the interface is the test surface — three table-driven cases (completed / errored / cancelled) exercise the whole end-of-turn contract, versus today's need to drive three separate event handlers.
  • Deletion test: deleting it would scatter the same precondition + flush + broadcast logic back across three handlers — it concentrates real complexity, so it earns its keep.
Candidate 2 · answers Q3

An explicit turn-substance predicate

Worth exploring
agent-service.ts — Message event handler (assistant insert) narrative-store.ts — buffers

Problem

"Don't bother saving if no agent action was recorded" has no place to live because there is no concept of recordable activity. The assistant row is committed on the Message event, before persistTurn ever sees the buffer — so by the time we could decide "this turn was empty," the row is already in the DB. An errored turn that produced one empty assistant message still leaves a hollow row in the thread.

Solution

Define hasRecordableActivity(threadId) = any buffered tool call, OR non-empty assistant content, OR any narration segment / hook. Move the assistant-message insert behind the finalize seam (Candidate 1) — buffer the streamed body the way tool calls are already buffered, and write it during finalizeTurn only when the predicate holds. An errored or cancelled turn with nothing to show clears its buffers and writes no row.

Before — row committed on a separate event, can't be un-decided

After — one gate decides the whole turn

flowchart LR M[Message event] --> BUF[buffer body] BUF --> FT[finalizeTurn] FT --> G{recordable?} G -->|yes| INS[(write row + narrative)] G -->|no| DROP[drop, no row] style G fill:#0c1f33,stroke:#60a5fa style INS fill:#0c2a1b,stroke:#22c55e

Benefits

  • Locality: the "is this turn worth keeping?" rule is one named predicate, not an emergent property of which event fired first.
  • Leverage: trivially unit-testable in isolation; the finalize seam consumes it as a guard.
  • Trade-off to grill: buffering the assistant body defers the Message broadcast slightly, and the client already renders streamed text live — so the persisted-row timing changes, not the user-visible stream. Worth walking the client contract (threadStore Trap 3) before committing.
Candidate 3 · prerequisite for retry

Idempotent assistant-message write

Worth exploring
message-repo.ts — create() narrative-store / repos already use INSERT OR IGNORE

Problem

The whole turn is almost re-runnable: tool calls, thoughts, and hooks all INSERT OR IGNORE on stable UUIDs. The assistant message is the one hole — a plain INSERT with no existence check. Any double-fire of the Message event (reconnect replay, or a retry in Candidate 4) silently duplicates the assistant row. The pipeline advertises idempotency everywhere except the one row that matters most.

Solution

Give the assistant message a deterministic identity for the turn (e.g. a per-turn id, or INSERT OR IGNORE keyed on (thread_id, sequence)) so re-running finalizeTurn is a no-op rather than a duplicate. This closes the asymmetry and makes the entire turn-finalize operation safely repeatable — the precondition that makes Candidate 4 sound.

Benefits

  • Locality: one consistent idempotency story across every table the turn touches.
  • Leverage: "the turn is re-runnable" becomes a guarantee callers (retry, reconnect replay) can lean on, instead of a per-table accident.
  • Tests: "call finalizeTurn twice → exactly one assistant row" is a single assertion.
Candidate 4 · answers Q4

Error classification + retry policy at the turn boundary

Speculative
agent-service.ts — Error handler claude-provider.ts — error event source prior art: handoff B/A/D classified-error + session resume-then-fallback

Problem

The Error handler treats every failure identically: persist-or-discard, mark the thread errored, stop. But you specifically want to auto-retry known failures that are sure to pass on a second try — a stale pooled session, a subprocess spawn race, a transient network blip. Today there is no notion of "transient vs fatal," so a retryable blip costs the user a manual re-send.

Solution

Add a small classifyTurnError(err): "transient" | "fatal" adapter and a retry policy consulted inside finalizeTurn's errored branch: if transient and attempts < N, re-issue the same buffered user message against a fresh session instead of finalizing an errored turn. The codebase already has the two ingredients — the handoff pipeline classifies provider errors into handoff.json, and the Session runtime already does "resume-then-fallback" on stale sessions. This lifts that instinct up to the turn level.

Before — every error is terminal

After — classify, retry the safe ones

flowchart TD E[error event] --> C{classify} C -->|"transient and attempts under N"| R[re-issue same user msg fresh session] C -->|fatal| P[finalize errored turn] R --> C style C fill:#0c1f33,stroke:#60a5fa style R fill:#0c2a1b,stroke:#22c55e

Benefits

  • Locality: "which errors are worth retrying" is one classifier table, not folklore spread across handlers.
  • Leverage: two adapters (classify + retry) behind one boundary turn a class of papercuts into invisible self-heals.
  • Depends on: Candidates 1 & 3 — retry is only safe once finalize is one seam and the assistant write is idempotent. Attempting this first would multiply the duplicate-row bug.
  • Grill first: what is provably "sure to pass"? Over-broad classification risks retry storms on genuinely fatal errors. Start with an explicit allowlist of 2–3 known-transient signatures.

Top recommendation

Start with Candidate 1 — the finalizeTurn(outcome) seam. It is the keystone: it is the only candidate that pays off on its own (collapsing three reasoning sites into one, and giving cancelled/errored their own outcome), and it is the home that Candidates 2, 3, and 4 all plug into. Your two questions — "don't save no-op turns" and "auto-retry known failures" — are both really asking for a single place that decides what ending a turn means. Build that place first; the empty-turn guard (C2) and the retry policy (C4) then become small decisions inside it rather than new scattered branches, with C3 as the idempotency prerequisite that makes retry safe.

Sequence: C1 → C3 → C2 → C4. C1 and C3 are mechanical and low-risk; C2 touches the client-render contract (narrative Trap 3) and deserves a grilling pass; C4 is the highest-value but should land last, behind an explicit transient-error allowlist.
