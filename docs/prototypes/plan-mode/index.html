Plan mode · side-panel architectures

Four ways to architect the panel, not four ways to arrange it.

The first round just moved the versions around. This round asks the real question: how should plan mode live inside a tabbed side panel, and how does that hold up when the content changes? Each prototype is a different structural answer, and each ships with a state toggle (keys 1–5) so you can watch the same architecture reflow across every case, including the one that started this: a docket with no plan above it. The glowing Implement placement you liked is kept constant throughout.

What's different from round one

  • The panel itself changes. Tabs appear and disappear; the panel reverts to normal; plan and todos merge or split. Not just furniture moved inside one fixed frame.
  • The empty top is solved per architecture, not patched. Each answers "can we still dock at the bottom?" differently.
  • The plan↔todo relationship varies on purpose: independent, derived-but-standalone, Scope-owned, or inseparable. Pick the relationship and the architecture follows.
  • Implement stays put. The glowing, always-visible button is constant, so you're comparing structure, not the part you already approved.

Four architectures

A

Two Tabs

Plan and Scope are separate sibling tabs. The Plan tab is dynamic: it spawns into the bar only when a plan exists and closes after Implement. Scope is permanent and carries a task count. "Todos but no plan" is just Scope with no Plan tab.

plan ↔ todo · independent · todos persist in Scope regardless of plan
Tab bar reshapesFamiliar mental model
B

Adaptive Dock

One tab holds both: plan docks top, docket docks bottom, with a resize divider. The split reflows per state, so with no plan the docket grows to fill the top, and with no todos the dock shrinks to a thin "derive tasks" strip.

plan ↔ todo · derived, standalone-capable · one surface, adaptive
Top never emptyLowest churn
C

Plan-mode Takeover

Plan is not a tab. When a plan exists it takes over the whole panel: the tab bar becomes a "Plan mode" banner with "Back to tabs", and the plan owns the surface. Implement, and it dissolves back to the normal tabs. Todos live in Scope.

plan ↔ todo · Scope-owned · derived tasks pushed to the Scope tab
Most focusBiggest overhaul
D

Unified Checklist

The plan is the to-do list. Every step is a checkable item whose prose expands inline; checking items off is implementing. There's no separate docket, so "todos without a plan" is simply the same checklist stripped of narrative.

plan ↔ todo · inseparable · one object, progress = implementation
No dock at allMost opinionated
