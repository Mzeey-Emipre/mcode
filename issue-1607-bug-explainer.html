Issue #1607: deletion, identity, and the Subagents panel

This memo records the deletion leak in #1607 and the later chat-to-panel navigation defect. It describes the provider-neutral view contract used for both.

Correct mental model: provider-native subagents belong in the Subagents panel. They are not Project tree nodes. An internal compatibility threads row remains a persistence detail and stays hidden while attached. The roster can show all children, but a selected detail view mounts only that child thread’s conversation.

Two defects at one boundary

#1607: deletion leak

Active-descendant retention detached provider-native children before recursive deletion. The delete queue then could not reach them, and the hidden compatibility row became a visible root.

Follow-up: wrong chat target

A chat subagent link needs the durable Mcode child ID. A provider operation ID or hierarchy label can name the activity, but it cannot select the child transcript.

Shared correction

Each provider supplies one trusted SubagentPresentation. The shared UI reads the provider-neutral detail target and never parses a provider prefix.

Evidence from Codex App Server

Spawn has three identities

A spawn end carries call_id for the operation, sender_thread_id for the parent, and new_thread_id for the durable native child Thread.id. AgentPath shows display hierarchy. It is not a durable child identity.

Codex protocol: collaboration events and AgentPath

Items and reads are thread-scoped

Generic item notifications carry thread_id, turn_id, and item_id. Child details are read by the child thread_id. A Thread also exposes parent, status, nickname or role, provider, model, and turns when requested.

App Server v2 item notifications · App Server v2 Thread data · App Server v2 Thread requests

Child control stays with the owner

A parent-owned V2 child cannot accept direct App Server input. Follow-up and resume go through its owner or parent. The App Server has no UI-open request, so Mcode maps the native child identity to its canonical child thread ID and opens the panel locally.

App Server direct-input guard · App Server request processor registry · App Server parent-owned child handling

Fact The linked Codex types define event and thread identities. Design conclusion Mcode owns local panel navigation because the provider does not expose a UI-open primitive.

Provider-neutral subagent view contract

CodexCollaborationEventAdapter uses childThread.id returned by durable delegation creation. Provider ingress removes any provider-supplied presentation before that server adapter runs. Claude, Cursor, or another adapter can emit the same contract. A server-authoritative Mcode target uses canonical-child. A provider-native identity uses canonical-alias and resolves only when one roster row matches. An ambiguous alias does not open a transcript. A provider without either target uses transcript-unavailable.

Persistence tags child and alias values with different versioned markers. Untagged historical values load as aliases. This prevents a provider identity from becoming a false Mcode thread ID after reload.

Follow-up fix: click one chat child, mount one conversation

The selection store receives detail.threadId. The panel resolves that canonical roster row, then passes only row.id to MessageList. It does not mount a parent transcript or a combined child transcript.

Deletion boundary: retain user work, delete provider children

Active-descendant retention now excludes rows whose canonical_agent_threads.parent_thread_id is non-null. A user-visible descendant can detach and survive. A provider-native child stays attached, so recursive hard delete removes it with its parent.

Implemented rule. Provider-native child C remains attached. The recursive delete queue reaches and removes it with parent P.

Historical evidence

The real-code memory-database probe reproduced the leak: the parent was absent, the child survived, parent and owner links were null, canonical root equaled self, and listByWorkspace() returned the child.

Migration 0053 repair

The repair identifies old orphans by the generated thread:codex-child:% namespace, a matching canonical row, Codex provider, null canonical parent and owner, and self root. Title Sub-agent is only a supplementary guard. It removes nested descendants and canonical history.

Why this was allowed

Facts

  • One parent field mixed lifecycle ownership and UI visibility.
  • Operation IDs, native child IDs, and canonical Mcode child IDs were conflated.
  • Tests proved components in isolation, but did not cover mixed ownership or the real chat-to-panel identity handoff.

Inference

The shared field and ambiguous identity roles let a value remain valid in one layer while it was wrong in another. The missing mixed-path coverage left both the deletion and navigation boundaries unproven. This describes a system boundary, not individual fault.

What the implemented design now proves

Deletion A provider-native child remains attached and recursive hard delete removes it. A user-visible delegated descendant can still detach and survive.

Navigation A chat click targets the canonical child thread ID. The panel finds that row and mounts its conversation only.

Extensibility A provider adapter can expose a durable mapped child. If it cannot, the UI reports that its transcript is unavailable instead of guessing.
